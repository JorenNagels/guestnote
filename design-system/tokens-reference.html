The logo colours are not UI colours

The mark’s teal and gold both sit at OKLCH L ≈ 0.80. Different hues, same lightness — no tonal contrast against each other, ~1.8:1 on white.

Fine for a logo, which is exempt from WCAG 1.4.3 and 1.4.11. Not fine for text, borders, state or chart series. The two hexes stay frozen; the UI draws from ramps on the same two hues.

Six RSVP states, not three

The spec forces this. G4 makes RSVP per-event — ceremony, dinner, party — so attending isn’t binary. G9 adds plus-ones, so a guest can have replied while their +1 is still unnamed. Both are things a planner must act on.

Declined is neutral, not red. A polite no is not an error. Painting declines red makes a healthy guest list look like a fire and teaches the planner to ignore red — so red is reserved for what’s genuinely broken: a dead address, a shuttle past capacity.

Every chip is dot plus label, never colour alone. The D2 place-card and D3 caterer exports get printed in mono at a venue.

Run through a colour-vision validator, not eyeballed. The status hues are reserved — never reused as a series — so the categorical set avoids them. Assign in fixed order; never cycle.

--border has no minimum: WCAG 1.4.11 covers control boundaries, not decorative dividers — a table with 3:1 gridlines is a spreadsheet from 1997. --input does: a field’s edge is what tells you the control is there.

Because it’s mostly tables

Numeric columns are right-aligned with tabular-nums in @layer base, so headcounts line up without per-table work. Rows separate by hairline, not zebra — zebra fights the status chips and breaks under filtering. Sticky header, sticky guest-name column when narrow. [data-density="compact"] drops rows 44px→32px for a 300-guest list.

Empty, loading and filtered-to-zero are three states with three messages. “No guests yet” and “No guests match these filters” are different problems for the person reading them.
